# Live_Clipping 🎬 — v1.3

Turn a YouTube live stream (or any public YouTube video) into vertical
**Shorts-ready clips** — automatically finding the loudest, most hype
moments. Built for a GTA 6 clipping channel: paste a stream link
(e.g. a Ducky Bhai GTA 6 live), the app captures it live, finds the
top moments from real audio energy, and cuts vertical Shorts at **Max
quality** (4K source → 2160×3840, 2K → 1440×2560, otherwise 1080×1920)
with a title, description, hashtags and source credit for each one.

**The flow (v1.1+): laptop cuts → Drive keeps → laptop frees space.**
Each clip uploads IN SEQUENCE to Drive
`Live_Clipping/07-cuts-sequence/<YYYY-MM-DD_Channel_video-id>/`
as `001_…mp4`, `002_…mp4`… right after it is cut. Once an upload is
verified, the local copy is deleted (default ON), so the laptop never
holds a whole job's clips. The next work — titles, thumbnails, posting
— is received from Drive, not from the laptop.

Cross-platform: **macOS, Windows, Linux**. Python 3.11+, ffmpeg + yt-dlp
(+ rclone for Drive upload). No paid APIs, no API keys. Panel is
localhost-only.

> ⚠️ **Rights note — please read:** only clip streams you own or have
> permission for, or that are fair-use / transformative with source
> credit. Every clip generated by this app carries its source channel
> and stream link. Do not remove that credit.

## Full flow — link → live analysis → review → approve → upload later

1. **Paste a link** (live stream or VOD) in the panel.
2. **Live analysis on the laptop**: a live stream is captured live in
   real time (segments), a VOD is downloaded at Max quality in the
   chosen time range. Moments are found from real audio energy.
3. **Clips go to Drive in sequence**: each cut uploads to
   `Live_Clipping/07-cuts-sequence/<stream-folder>/` as `001…`, `002…`,
   verified, then the local copy is deleted to keep the laptop light.
4. **Review / edit / approve in the panel**: every clip shows its
   preview, score, timestamp, title, description and hashtags. You can
   edit the title/description/hashtags, trim start/end by seconds
   (needs the source still on the laptop), and press **Approve for
   upload**. Approval sets `approved=true` + `approved_at` in
   `clips.json` and in the Drive manifest
   (`<stream-folder>_manifest.json`) — it does **not** publish
   anything by itself.
5. **Upload later, outside the laptop app**: Buzz reads the approved
   clips + manifest from Drive and uploads the approved ones to your
   channel via Postiz (once the channel is connected). This app has
   **no YouTube OAuth and no YouTube upload code** — deliberately.

## Live progress — survives a browser refresh

The panel shows live progress, not just a stage name:
- **VOD download**: bytes downloaded, total size when known, % and
  speed (MB/s), from yt-dlp progress + the part-file size on disk.
- **Live capture**: recording elapsed time, segments captured, current
  moment count, and a pulsing red **LIVE** indicator. A live stream
  has no total size, so no fake % is ever shown.
- Every job (panel, CLI, rerun script) writes progress to
  `~/YT/live_status.json` on every stage change, and `/api/status`
  reads that file from disk on every request — so a refresh shows the
  live work, not a stale previous job. The log tail is also read from
  the log files on disk (`logs/live_clipping.log`, `logs/rerun_1h.log`).

## How it works

1. **Paste a link** in the panel (or pass `--url` on the CLI).
2. **Fetch** shows the title, channel, live/VOD status, duration and thumbnail.
3. **Process**:
   - Live stream → **captured live while it runs** (primary: yt-dlp
     records the live stream itself for the time you choose; fallback:
     ffmpeg HLS capture in 60 s segments, so a lost stream only loses
     the current chunk). The panel shows LIVE CAPTURE status: method,
     elapsed time and segment count. Upcoming (not started yet) streams
     are refused with a clear message — never a fake success.
   - Finished stream / VOD → downloads at Max quality by default, in
     the time range you choose (Auto = first 1 hour for videos over
     2 hours, otherwise full — an 11-hour VOD is never downloaded whole
     by default).
   - Audio is extracted and RMS energy is measured in 1-second windows.
     Peaks above your sensitivity threshold are merged (within 15 s) and
     ranked. Subtitle keywords (`clutch`, `insane`, `wow`, `GTA`, `Vice
     City`, `Lucia`, `Jason`…) give a +10 boost when subtitles exist.
   - Each top moment is cut centred on its peak, cropped/scaled to
     vertical **2160×3840 (4K source) / 1440×2560 (2K) / 1080×1920,
     30 fps, CRF 18, AAC 192k, loudnorm**, max 60 s. A source lower
     than the target is upscaled (lanczos + unsharp + light denoise)
     and the clip is labelled `upscaled from 720p` (or whatever it
     was) in `clips.json` — never claimed as native 4K.
   - **Each clip uploads to Drive in sequence immediately after it is
     cut** (see Drive section below), and the local copy is deleted
     once the upload is verified (default ON).
4. **Clips queue**: preview each clip in the browser (or see “in Drive
   now” if its local copy was freed), see its score / timestamp /
   title / Drive status, download it, copy its title + description,
   retry a failed Drive upload, mark it as Posted (moves it to
   `posted/`), or delete it.

## Install

### Requirements
- Python 3.11+ — `python3 --version`
- ffmpeg + ffprobe in PATH — `ffmpeg -version`
- yt-dlp — `pip install yt-dlp`

### macOS
```bash
brew install ffmpeg yt-dlp python
pip install -r requirements.txt   # numpy is optional but faster
./run_mac.sh                      # opens http://127.0.0.1:8899
```

### Windows
```powershell
winget install Python.Python.3.12 Gyan.FFmpeg
pip install yt-dlp
run.bat                           # opens http://127.0.0.1:8899
```

### Linux (Kali / Debian / Ubuntu)
```bash
sudo apt install ffmpeg python3-pip
pip install --user --break-system-packages yt-dlp
pip install -r requirements.txt
./run.sh                          # opens http://127.0.0.1:8899
```

### Manual start (any platform)
```bash
python3 live_clipping.py --serve --port 8899 --data-dir ~/YT
# Panel: http://127.0.0.1:8899
```

### CLI (no panel)
```bash
python3 live_clipping.py --url "https://www.youtube.com/watch?v=XXXX" \
  --clips 5 --length 45 --sensitivity med
# Live stream, capture 30 minutes live first:
python3 live_clipping.py --url "<live-link>" --record-minutes 30 --clips 5 --length 45
# Long VOD, first hour only, keep local copies:
python3 live_clipping.py --url "<vod-link>" --vod-range 1h --no-free-space
# Max quality is the default; force 1080p:
python3 live_clipping.py --url "<link>" --quality 1080p
```

## Drive upload — sequenced, automatic (v1.1+)
Each clip is uploaded by the app itself, in cut order, to
**Live_Clipping / 07-cuts-sequence / `<YYYY-MM-DD_Channel_video-id>/`**
(Drive folder id `1MLzGI9qbzD2Ms8_305bByQgGfGe-If4b`), as
`001_…mp4`, `002_…mp4`, `003_…mp4`. The upload is verified with
`rclone ls` (name + size must match) before the local copy is freed.
A failed upload keeps the clip local as **Pending** with a Retry
button in the panel — nothing is ever deleted before its upload is
verified. After the job, the big source download is deleted only if
you ticked “Delete source after job” AND every clip is in Drive.

Prerequisite — rclone with a `[gdrive]` remote. The app finds rclone
in PATH, `~/go/bin`, `~/.local/bin`, `/usr/local/bin`, `/usr/bin`
(the laptop has it at `~/go/bin/rclone` and `~/.local/bin/rclone`,
v1.75.2, config `~/.config/rclone/rclone.conf`). Verify it with:
```bash
rclone lsd gdrive:Live_Clipping
rclone ls gdrive:Live_Clipping/07-cuts-sequence/<stream-folder>/
```
If rclone is missing, clips stay local as Pending and the panel says
so — the job still cuts clips, it just does not free laptop space.
The app never prints or logs the rclone token.

Drive layout: `01-clips-ready`, `02-raw-moments`, `03-sources`,
`04-titles-thumbnails`, `05-posted`, `06-app-builds`,
`07-cuts-sequence` (the sequenced cuts). Next work (titles /
thumbnails / posting) is received from Drive, not from the laptop.

## Settings explained
- **Clip length** 30 / 45 / 60 s — Shorts must be ≤ 60 s.
- **Number of clips** 3 / 5 / 10 — top moments by energy score.
- **Sensitivity** Low (only the loudest peaks) / Medium / High (more, quieter moments).
- **Live record time** — how long a live stream is captured before analysis.
- **Quality** Max (best available — 4K if the stream has it) / 4K / 2K / 1080p.
  Max never downscales a better source; a lower source is upscaled and
  labelled honestly.
- **VOD time range** Auto (first 1h if the video is over 2h, else full) /
  Full / First 30 min / First 1 hour / First 2 hours.
- **Free laptop space after Drive upload** (default ON) — delete the local
  clip once its Drive upload is verified.
- **Delete source after job** (default OFF) — delete the source download
  only if every clip is safely in Drive.

## Troubleshooting
- `yt-dlp is not installed` → `pip install yt-dlp` (see Install).
- `ffmpeg not found` → install ffmpeg and make sure it is in PATH.
- `This stream has not started yet` → the link is a scheduled stream; wait until it is live.
- `YouTube asked for a sign-in / bot check` → YouTube is rate-limiting that
  video; try again later or use a different public video.
- `Could not get the live stream URL` → fixed in v1.2 (see below); if it
  still happens, the stream may have ended, or YouTube refused the
  format — the error now shows yt-dlp's own last line. The app retries
  once, then falls back to ffmpeg segment capture.
- `Live capture failed` (both methods) → the stream ended mid-capture or
  YouTube refused it. Try again while the stream is live.
- Drive upload stays Pending / Failed → rclone or the `[gdrive]` remote
  is missing (check `rclone lsd gdrive:Live_Clipping`); fix rclone, then
  use the Retry button in the panel. The clip is never deleted before a
  verified upload.
- Clip audio is quiet → loudnorm is applied; check the source stream volume.
- Panel shows old clips → clips are listed from `clips.json` in your data dir;
  delete from the panel to remove the file too.

## v1.3 — face-centred framing, default for all videos (2026-11-17)
A 9:16 vertical crop only keeps the middle third of a 16:9 frame, so a
face standing left or right of centre got cut off — found on the GTA 6
"Extended Look" combined clip (street shooter far-left, office speaker
right-edge). Framing is now set by what is actually in the shot, not
by the frame centre, and it is the **default for every video**:
1. **Face** — the engine samples the segment with OpenCV **YuNet**
   (`engine/face_framing.py`, model
   `engine/models/face_detection_yunet_2023mar.onnx` bundled, ~233 KB),
   picks the face closest to the frame centre per sampled frame, and
   centres the crop on the midpoint of that face's travel — so the crop
   covers the whole movement. The face's vertical position is used too
   whenever the frame has vertical slack.
2. **Motion** — when no face is found, the crop follows the strongest
   motion in the segment (the action), measured from small grayscale
   frames; scene cuts are skipped and uniform motion (a pan) falls
   through to centre.
3. **Centre** — when neither is usable, the crop stays centred, and
   the log says so. Nothing ever fails the cut: every fallback is
   logged and the clip is still made.
Haar cascades were tested first and rejected (found faces in only 4 of
24 test frames; YuNet found 14). Use it from the panel (Framing →
Face-centred, now the default), per clip (Face focus button), or CLI
`--focus face` (default); `--focus gameplay` goes back to the plain
centre crop. Requires `opencv-python-headless==4.10.0.84` (see
requirements.txt); **do NOT use 5.x** — it removed face detection
entirely. Without OpenCV, face detection is skipped and the motion
fallback still runs (it only needs numpy).

## v1.2 fixes — WEEI live failure (2026-11-17)
The WEEI Boston Sports live stream (Y6JZ4yzZNAw) failed twice at 07:09
and 07:13 with “Could not get the live stream URL. The stream may have
ended.” — but the stream was live and healthy. Root cause, found by
reproducing it: the old code asked yt-dlp for `-f "b[height<=1080]/b"`.
Live streams have NO combined format `b`, only separate HLS video/audio
formats, so yt-dlp answered “Requested format is not available”. Fixed:
the live URL selector is now `bv*+ba/b` (video URL + audio URL), with a
retry, and live capture now tries yt-dlp live download first (verified
playable with ffprobe) and falls back to ffmpeg 60 s segment capture.
Verified against the still-live WEEI stream — see TEST_REPORT.md §9.
